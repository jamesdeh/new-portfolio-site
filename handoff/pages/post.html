W03/12: Reading before writing

Week three was mostly reading: design docs, old reviews and a lot of git log. This is the checklist I ended up using to read for risk before touching any code.

01Why reading first

I came in expecting to write code from day one. Instead, most of week three went on reading. It felt slow on Monday. By Friday it felt like the job.

Security review is mostly questions, and you can't ask good ones about a system you haven't read. So the first skill is reading quickly without skimming past the risky parts.

Note

Everything in this series is public knowledge or my own opinion. Nothing internal, nothing under NDA.

02The checklist

I borrowed the shape from STRIDE1 and cut it down to five questions I can answer from a design doc in about twenty minutes:

  • Where does data cross a trust boundary, and who checks it on the way in?
  • What happens if this request is replayed, reordered or sent twice?
  • Which secrets does this touch, and where do they live at rest?
  • What does the log line look like when this goes wrong?
  • Who can change this config, and would anyone notice?

03A small example

One pattern I now look for straight away: parsing untrusted input with a loader that can build arbitrary objects. In Python the classic one is YAML.

Warn

Don't pass untrusted YAML to yaml.load with the full loader. Use yaml.safe_load unless you can say exactly why not.

It's an old, well-documented bug class2, which is the point. Reading for risk is mostly spotting old patterns in new code.

04What I'd tell week-one me

Read the boring parts. That's where the assumptions live.
